## 0. 定稿链路

```
用户 Query
   ↓
安全层（不变：长度截断 + 敏感词 + 攻击拦截）
   ↓
规则预检（YAML 词表，零成本快速通道）：
   命中指代/对比/省略/反问特征词？
   ├─ 命中 → LLM 统一调用（带对话历史）：改写 + 输出 scene
   └─ 未命中 → LLM 统一调用（不带历史）：改写 + 输出 scene
        （同一次调用：query 自包含则 rewritten_query 原样返回）
   ↓
scene 合法性校验（白名单，枚举见议题 2）
   ↓
按 scene 过滤 RAG 检索（file_name 精准检索）
   ↓
Top-K 话术 + 扩展话术 拼 Prompt → LLM 生成回复
```

**一次 LLM 调用合并**：改写与场景识别合并为一次调用，缩短用户等待时间。
prompt 写明"query 自包含则 rewritten_query 原样返回，有指代/省略/反问则结合
历史补全为中立的完整问题"。temperature=0。

## 议题 1：规则预检的触发词 ✅ 已定

**决议**：

- **词表放 YAML 配置**（后续可接配置中心随时调整）——因为预检词只能想到一部分，
  无法一次列全，需要持续运营迭代；
- **纳入"反问型"**（"难道""不会吧"）：反问**需要** LLM 改写——反问包含人的主观情绪，
  不改写会导致 RAG 匹配度过差；场景由 LLM 在改写时一并给出；
- **预检的定位**：只是一个"是否进 LLM 改写"的快速判断通道，除此之外不做任何决策。
  即使预检失误，影响也不大——走了 LLM 本身就比 HF 模型安全。

参考示例 `doc/reference/1-Query改写.py` 的五类划分（上下文依赖 / 对比 / 模糊指代 /
多意图 / 反问）及其触发词，作为 YAML 词表的初始内容。

- 返回 JSON：`{"rewritten_query": "...", "scene": "..."}`，解析失败有兜底；
- temperature=0（示例代码已这么做，保留）。

## 议题 3：置信度评分 ✅ 已定

**决议**：LLM 输出里**保留 `confidence` 字段，但只记日志不参与决策**。

理由：LLM 自报置信度是校准很差的主观分数，换措辞就飘；但直接丢掉又少了一个
观测口子。先攒一批日志、人工对照验证准不准，再决定将来是否启用阈值决策。

## 议题 4：分析失败的兜底 ✅ 已定

**决议**：**直接走 LLM，跳过 RAG**。

理由：话术库目前只有 5 个 md，全塞进提示词都放得下；RAG 检索可能引入语义近似
但场景错误的话术，造成**误导**——"有意思"是锦上添花，"答对答错"是对错问题，
宁可朴素不可误导。

LLM 调用失败或 scene 非法时的兜底：
- JSON 解析失败 / scene 不在枚举内 → 跳过 RAG，直接用原始 query 走 LLM 生成；
- LLM 调用本身失败（超时/限流）→ 返回兜底话术（"系统开小差了"），记日志。

## 议题 5：树洞双保险 ✅ 已定（澄清）

树洞**不是** RAG 场景枚举之一（话术目录没有树洞.md），它是 system prompt 层的
安全协议：连续两次极度负面情绪 → 终止玩笑、只做陪伴。硬触发、错不起。

**决议**：LLM 判出极度负面情绪时，对原文再跑一次廉价正则校验（命中"不想活了"
等强信号才确认触发安全协议），确认不了按普通安慰处理；触发记日志便于复盘。
属 prompt 层规则，不进 scene 枚举，不进 RAG 过滤。

## 议题 6：历史对话的携带与记忆 ✅ 已定（含新方案：分级记忆）

**预检与历史的关系**（维持决议）：预检命中 → 带历史进 LLM；未命中 → 不带。

**历史轮数问题**：不再设固定轮数 N，升级为下面的分级记忆方案。

### 分级记忆方案（用户提出，已采纳方向，细节待实现时定）

> 灵感：为省存储只保留近期历史，远期历史压缩归档，靠 RAG 召回；保留时长
> 做成商业化开关（默认一周，用户多了缩短，买套餐延长）。

```
查找顺序（命中即停）：
  1. 当前对话窗口（最近若干轮，未压缩）
  2. 压缩后的历史摘要（LLM 定期把过期对话压缩成摘要）
  3. RAG 归档的历史对话（远期全量对话向量化，按语义召回相关片段）
  4. 都没有 → 就当没有历史
```

存储分层（与架构演进.md 1.6 对齐，均**未实现**）：

| 层级 | 内容 | 技术 | 保留策略 |
| --- | --- | --- | --- |
| L0 当前窗口 | 最近 N 轮原文 | L1 内存 + L2 Redis | TTL 1 小时滑动过期 |
| L1 压缩摘要 | 过期对话的 LLM 压缩摘要 | Redis/PostgreSQL | 默认保留一周（可调，套餐可延长） |
| L2 RAG 归档 | 远期全量对话的向量化片段 | Chroma（独立 Collection） | 受 L1 保留策略约束 |

**实现要点与风险（实现时需评估）**：
- 压缩时机：对话空闲 N 分钟后触发，或定时任务批量做；压缩用 LLM 有成本，
  需控制频率（这也对应"用户多了缩短保留时间"的动机）；
- RAG 归档的质量：闲聊对话向量化后语义召回的噪声较高，"找压缩摘要没有就走 RAG"
  这个顺序合理——RAG 历史只作兜底补充；
- 隐私与合规：对话归档涉及用户数据留存，套餐延长 = 付费换更长留存，
  产品上要在隐私条款里说清楚；
- 该方案对应 V1.x 演进，**V1.0 先只做 L0 当前窗口**（内存 + Redis），
  L1/L2 留接口不进实现。
- 窗口按用户隔离。`user_id` 由 Go 网关验签后以请求头 `X-User-Id` 传入，
  Python 不在 Agent 内再解 JWT（见《预检与LLM统一调用-设计稿》「用户身份」）。
  无此头时历史按空处理。Redis 键：`chat:window:{user_id}`。
