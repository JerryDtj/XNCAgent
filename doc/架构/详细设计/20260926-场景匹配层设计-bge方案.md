# 场景匹配层设计——bge 句向量方案（2026-09-26）

> 状态：**已定稿并落地（2026-09-26）**，实现见 `xncagent/scene_matcher.py`；
> ADR 记录见《架构演进.md》ADR-010（ADR-001 同时标记废弃）。
> 背景：HF 零样本分类（NLI 范式）实测不达标，本稿记录替代方案的选型证据、
> 定稿设计与评测框架。主链路（预检 → LLM 统一调用 → RAG）不受影响。

***

## 0. 背景：HF 零样本分类为什么被放弃

### 0.1 问题起源

`scene_classifier.py` 最初用 `facebook/bart-large-mnli` 做中文场景分类，
用户实测反馈：输入"哈哈哈，笑死我了"被分到"安慰话术"（置信度 0.76）。
bart-large-mnli 是纯英文 NLI 模型，不适合中文。

### 0.2 换多语言模型后的三组实验（2026-09-26，mDeBERTa-v3-base-mnli-xnli）

| 实验  | 做法            | 结果                                   | 结论               |
| --- | ------------- | ------------------------------------ | ---------------- |
| 实验一 | 6 标签 + 中文假设模板 | "哈哈哈"→ 无关闲聊 ✓，但"唉，不想起床"→ 无关闲聊（0.67）✗ | 兜底式标签误伤正经场景      |
| 实验二 | 5 标签 + 低分兜底   | "我失恋了，心里好难受"各标签分数全平（\~0.2）→ 误判兜底 ✗   | 情感场景漏判，情感陪伴场景错不起 |
| 实验三 | 句向量方案（本稿方案）   | 见第 1 节                               | 错误模式可控，可行        |

**根因**：NLI 零样本分类永远不会"弃权"——它只在候选标签里硬挑最高分；
而"无关闲聊"是个元标签（"以上都不是"），NLI 模型很难对否定式假设打出高分。
"必须有弃权能力"和"NLI 零样本"是范式级冲突，调模型解决不了。

***

## 1. 模型选型：36 条评测集实测对比

`test/scene_match_eval.py` 跑 `test/scene_match_cases.yaml`（36 条，8 类），
同阈值 0.45，2026-09-26 实测：

| 指标                | BAAI/bge-small-zh-v1.5 | shibing624/text2vec-base-chinese |
| ----------------- | ---------------------- | -------------------------------- |
| **总体准确率**         | **32/36 = 88.9%**      | 27/36 = 75.0%                    |
| 参数量 / 维度          | 24M / 512 维            | 102M / 768 维                     |
| edge\_slang（网络新词） | 2/3                    | **0/3**                          |
| hit\_挨骂兜底         | 4/4                    | 2/4                              |
| hit\_职场吐槽         | 4/4                    | 4/4                              |
| hit\_安慰话术         | 5/5                    | 5/5                              |
| compound（复合意图）    | 3/3                    | 3/3                              |
| fallback          | 4/6                    | 4/6                              |

**选型结论：`BAAI/bge-small-zh-v1.5`**。理由：

1. **准确率全面领先**，网络新词和"挨骂兜底"差距明显——这两个恰是
   情感陪伴 agent 的高频输入；
2. **体积小 4 倍**，2核4G 目标机器上加载快、内存省、相似度计算便宜；
3. **血统对口**：bge 为检索任务（query → 文档）训练，本场景是
   "用户一句话 → 场景描述"的非对称匹配；text2vec 偏对称 STS 任务；
4. 错误模式更友好：闲聊样本最高分普遍压在 0.4\~0.5，阈值兜底接得住。

**两者共同的难点**：纯笑声（"哈哈哈""笑死我了"）与"捧哏金句"的边界——
这是产品口径问题而非模型问题，见议题 2。

## 2. 定稿设计

### 2.1 匹配机制

```
用户 query
   ↓ encode（normalize_embeddings=True）
与 6 个场景描述（scene_desc.yaml）算余弦相似度
   ↓
top1 分数 ≥ threshold(0.45) → 该场景
top1 分数 <  threshold        → 无关闲聊（兜底）
```

* bge 的短 query 检索指令前缀（"为这个句子生成表示以用于检索相关文章："）
  针对"短 query → 长文档"检索设计，本场景是短对短匹配，**不加**；

* 相似度必须 `normalize_embeddings=True` 后内积（bge 输出不归一化）；

* 复合意图当前取 top-1 即可（命中任一期望场景即算对，评测集已覆盖）；
  若未来 RAG 需要按多场景检索，接口需返回 top-k 而非 top-1（预留，见 5.3）。

### 2.2 配置：`xncagent/config/scene_desc.yaml`

```yaml
threshold: 0.45
fallback_scene: 无关闲聊
scenes:
  挨骂兜底: 主人在吐槽、责骂小喜子本人，比如说它贱、让它闭嘴、想打它，小喜子需要用自黑幽默兜底
  安慰话术: 主人emo、自我怀疑、情绪低落、失恋、人际敏感，需要安慰和共情
  ...
```

描述口径与《20260925-Query理解层设计讨论.md》议题 2 的场景枚举**严格对齐**：
**"挨骂兜底"仅指主人吐槽小喜子本人**，用户被老板骂属于"职场吐槽"。
每个场景一句话说清"谁在什么状态下需要什么"，写长了会稀释向量。

### 2.3 函数签名

```python
def match_scene(query: str) -> tuple[str, float]:
    """
    场景匹配：返回 (场景名, top1 分数)。
    top1 分数低于配置阈值时返回 (fallback_scene, top1 分数)。
    调用方如需观测，可记日志；模型常驻内存，首次调用加载。
    """
```

## 3. 与现有架构的衔接

### 3.1 主链路不变

2026-09-25 定稿链路（预检 → LLM 统一调用 → scene 白名单校验 →
按 file\_name 精准检索 RAG → 生成）**不受影响**。本组件不替代 LLM 场景识别。

### 3.2 本组件的两个角色（推荐都做，成本低）

| 角色        | 触发                                    | 行为                                                             |
| --------- | ------------------------------------- | -------------------------------------------------------------- |
| A. 本地降级通道 | LLM `understand_query` 超时 / 限流 / 解析失败 | 用 `match_scene` 结果代替 LLM 的 scene 走 RAG，失败兜底话术不变                |
| B. 交叉校验观测 | LLM 正常返回                              | 每次调用**全量**记录 `matcher_scene, matcher_score`；两者不一致时额外记 WARN 日志。攒数据回归校准阈值（0.45） |

角色 A 落地时**删除 HF 零样本相关代码**：`scene_classifier.py`、
`scene_registry.py`、`xiaoxizi_agent.py` 中的 HF 分支——这是
`git rm` 级清理，ADR-001（mDeBERTa 零样本分类）标记废弃。

> **实现状态（2026-09-26）**：两个角色均已落地于 `xncagent/scene_matcher.py`
> + `xncagent/agent/xiaoxizi_agent.py`。注意：当前代码 WARN 日志仅在不一致时
> 记录 score——**全量 `matcher_score` 日志是实现时补强的点**（否则看不到
> 一致案例的分数分布，无法做阈值校准），已写入《20260925-预检与LLM统一调用
> -设计稿》的补记与日志字段要求。

### 3.3 RAG embedding 统一（独立步骤，不在本稿范围）

`script/build_knowledge_base.py` 当前用
`paraphrase-multilingual-MiniLM-L12-v2`（384 维）。若 RAG 也切到
bge-small-zh-v1.5（512 维）：向量维度不同**必须重建 Chroma 库**，
且 ADR-003 的选型论证需要增补一条修正记录。统一后知识库与场景匹配
共用一份模型内存，2核4G 上更划算。是否切见议题 3。

## 4. 评测框架

### 4.1 资产清单

| 文件                                | 作用                                       |
| --------------------------------- | ---------------------------------------- |
| `xncagent/config/scene_desc.yaml` | 场景描述 + 阈值（匹配器与评测共用同一份配置）                 |
| `test/scene_match_cases.yaml`     | 评测集，36 条种子用例，8 个类别，目标 ≥ 50 条             |
| `test/scene_match_eval.py`        | 评测脚本，`--model` / `--threshold` 可换模型换阈值对比 |
| `test/scene_match_report_<模型>.md` | 每次评测归档的报告（分组指标 + 错误明细 + 全量分数）            |

### 4.2 用例分类（补充用例时保持类别不变，指标才有纵向可比性）

| category                                | 含义                        | 条数 |
| --------------------------------------- | ------------------------- | -- |
| hit\_<场景>                               | 明确场景输入，期望命中               | 20 |
| fallback                                | 闲聊/低信息量，期望被阈值兜进无关闲聊       | 6  |
| compound                                | 复合意图，expected 为列表，命中其一即算对 | 3  |
| edge\_slang / edge\_short / edge\_other | 网络新词 / 极短输入 / 反问转述        | 7  |

### 4.3 基线与验收标准

* 当前基线（2026-09-26，阈值 0.45）：**bge-small-zh-v1.5 80.0%**（48/60，
  slang 组标注经 6 处口径复核修正后；修正前 76.7%，其中约一半是考卷标注问题）。

* 建议验收标准：总体 ≥ 90%；hit\_\* 分组 100%；**误判兜底 = 0**
  （正经场景被误判成无关闲聊是这套机制里最贵的错误）。

* 已知遗留错误："破防了"误判兜底（top1 仅 0.417，扩充 slang 用例后看是否缓解）；
  纯笑声口径已决议走捧哏（议题 2），评测集期望已同步修正，重跑基线后更新此处。

### 4.4 评测纪律

* 调阈值、改描述文案，必须以报告 diff 为依据，**不允许凭感觉改**；

* 每次改动跑两个模型的报告，防止为 bge 过拟合（评测集只有 36 条，
  有过拟合评测集的真实风险）；

* 用例集 ≥ 50 条之前，只做错误分析，不做阈值微调。

## 5. 风险与边界

1. **样本量小**：36 条不足以论高下，88.9% 的绝对值参考价值有限，
   看分组错误分布比看总分有用；
2. **阈值未经验证**：0.45 仅在评测集上成立，上线后靠角色 B 的
   交叉校验日志回归校准；
3. **top-1 接口预留**：复合意图当前取 top-1，若未来 RAG 按多场景
   检索需改为 top-k，签名在 2.3 已留余地；
4. **新词漂移**：网络 slang 更新快，描述文案和评测集需要随运营迭代，
   这正是把词表/描述放 YAML 配置的原因。
5. **多原型实验已否决（2026-09-26）**：曾把 `doc/场景定义/` 的"主人会这样说"
   例句编码为多原型（max 池化），60 条评测集从 46/60 退步到 31/60——
   例句都是极短口语句，闲聊输入与任何一句例句相似度都不低，而兜底场景
   "无关闲聊"没有例句只有抽象描述，max 池化让有例句的场景分数虚高、
   闲聊被淹没（"今天天气真不错"撞到安慰话术 0.60）。mean 池化（37/60）
   同样不及单原型。**结论：例句只用于 LLM prompt 和评测出题，不进向量原型。**
   该结论已写入 `scene_matcher.py` docstring 备查。

## 6. 议题决议（2026-09-26 已定）

| # | 议题                      | 决议  | 影响                                                                                                            |
| - | ----------------------- | --- | ------------------------------------------------------------------------------------------------------------- |
| 1 | 角色定位                    | 都做  | 落地时删 HF 零样本代码；LLM 正常返回时记不一致 WARN 日志                                                                       |
| 2 | 纯笑声口径                   | 走捧哏 | 评测集中纯笑声用例期望从"无关闲聊"改为"捧哏金句"；scene_desc.yaml 描述文案同步修正；与《doc/场景定义/00-边界与优先级.md》判例"哈哈哈笑死我了→捧哏金句"对齐 |
| 3 | RAG embedding 切换      | 切   | 需重建 Chroma（512 维 ≠ 384 维）+ 增补 ADR-003 修正记录；统一后省一份模型内存                                                          |
| 4 | 阈值策略                    | 可以  | 0.45 先上线只记日志，攒交叉校验数据后回归校准                                                                                        |

**口径权威来源（补充决议）**：场景判定规则以 `doc/场景定义/`
（五类场景定义 + 00-边界与优先级）为准——它定义了判定优先级链
（挨骂兜底 > 职场吐槽 > 安慰话术 > 捧哏金句 > 懒懒不想动）、工作锚点
和判例表。本稿的 `scene_desc.yaml` 是它的"机器可消费版"（向量原型），
LLM prompt 的场景枚举说明也应从它生成，做到**一处定义、多处消费**。
`doc/场景定义/` 不删除、不并入本文档：规则面向人和 LLM prompt，
本文档面向 embedding 匹配实现，两者互补。
