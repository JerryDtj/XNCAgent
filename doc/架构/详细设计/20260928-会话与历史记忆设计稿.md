## 0. 背景与目标

目标：Agent 聊天体验对齐 DeepSeek 前端——**聊天列表、点击列表还原上次对话状态、跨会话语义查询历史**。

参考：DeepSeek 给出的会话摘要设计（conversations / messages / conversation\_summaries 三表最小集 + 可选 FTS、分段摘要、message\_embeddings、memory\_facts）。**裁剪决议**：去掉 pgvector（向量已在 chroma，不引扩展、不动 compose）、去掉全文检索（中文无分词，见 D7）、memory\_facts 与分段摘要列二期规划（§7.4）。

现状与动机：

* 聊天接口只有一个 `message` 参数，无会话概念，消息不落库（`xncagent/route/agent_route.py`）。

* L0 历史是 `llm_task.py` 里的进程内 `_histories` 字典，进程重启即丢，且按 user 而不是按会话组织。

* `X-User-Id` 已贯通（Go 网关 JWT 解出注入头 → Python middleware 读入 ContextVar）。

* `init.sql` 头部注明 `chat_sessions` 原本规划在二期；因面试策略改为 **Agent 优先**，本设计将其提前到一期。

* 语义检索基础设施现成：bge-small-zh-v1.5（512 维）+ chroma + bge-reranker-base。

| #  | 议题        | 决议                                                                                                                                                                                                               |

| D3 | 跨会话查询     | **两级语义检索**（参考 DeepSeek 会话摘要设计裁剪）：消息级（chroma `chat_history`）+ 会话摘要级（新表 `chat_session_summaries`，摘要向量进 chroma `chat_summaries`）。复用同一 bge 嵌入实例与 reranker，metadata filter 做用户隔离。汉语同词多语境，LIKE 与 Postgres FTS 均不可用（D7） |

| D5 | 前端归属      | 前端（列表 / 还原 / 流式渲染 / 搜索框）交 Cursor 实现，**API 形状以本文 §4 为准，Cursor 不得自创字段**                                                                                                                                            |

| D7 | 全文检索      | **不采纳**：Postgres `to_tsvector('simple')` 对中文无分词，整句成为一个 token，GIN 基本检索不出内容；中文 FTS 需 pg\_jieba / zhparser 扩展（要动 compose 镜像），收益已被语义检索覆盖。确需精确匹配（如 ID 类字符串）临时用 `content LIKE '%...%'` 即可                              |

## 2. 领域归属与写入职责（D1 展开）

```
浏览器 ──► Go Gateway（JWT 鉴权 + 注入 X-User-Id + /agent/* 透传）
              │
              ▼
        Python Agent（会话/消息/摘要 API、L0、生成、写库、写向量）
              │
              ▼
        Postgres（chat_sessions / chat_messages / chat_session_summaries）
        chroma（chat_history 消息级 / chat_summaries 会话级）
```

* 聊天数据是 **Agent 域数据**：会话 CRUD、消息读写、摘要、语义搜索全部在 Python 实现，路由挂在 `/agent/*` 下，Go 反代自动覆盖，**Go 不加新 handler**。

* Python 通过 `DATABASE_URL` 直连 Postgres（asyncpg / SQLAlchemy async 任选，**.env 加载修复是前置项**）。

* user\_id 只允许来自 ContextVar（网关注入的头），**忽略客户端请求体里自带的任何 user\_id / session 归属字段**——写库时的 user\_id 以 ContextVar 为准，session 归属校验"该 session 的 user\_id == ContextVar user\_id"，防水平越权。

* 账务域（余额、流水）仍归 Go，与本设计无关；一期计费接入时 Go 只需要消息里的 `token_count`，不改变归属。

## 3. 表结构（DDL）

新迁移文件：`XNCAgent-go/deploy/postgres/migrate_0003_chat_sessions.sql`；同时把三张表并入 `init.sql`（全新环境首启用）并删除 init.sql 头部"不含 chat\_sessions"一句。

```sql
-- 8. 聊天会话（Agent 域；一期提前，原规划二期）
CREATE TABLE IF NOT EXISTS chat_sessions (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(100) NOT NULL DEFAULT '',
    status VARCHAR(20) NOT NULL DEFAULT 'active',
    message_count INT NOT NULL DEFAULT 0,
    last_message_at TIMESTAMP,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_chat_sessions_user_time ON chat_sessions(user_id, last_message_at DESC);

COMMENT ON TABLE chat_sessions IS '聊天会话列表；title 为空表示 LLM 标题未生成，前端回退首条消息截断';
COMMENT ON COLUMN chat_sessions.id IS '会话主键';
COMMENT ON COLUMN chat_sessions.user_id IS '所属用户，级联删除';
COMMENT ON COLUMN chat_sessions.title IS 'LLM 生成的短标题，≤12 字，可改名';
COMMENT ON COLUMN chat_sessions.status IS 'active / deleted（一期物理删除，status 预留）';
COMMENT ON COLUMN chat_sessions.message_count IS '消息行数（user+assistant 各计 1），每落一条消息同步 +1';
COMMENT ON COLUMN chat_sessions.last_message_at IS '最近消息时间，排序依据；消息落库时同步更新';
COMMENT ON COLUMN chat_sessions.created_at IS '创建时间';
COMMENT ON COLUMN chat_sessions.updated_at IS '最近更新时间';

-- 9. 聊天消息（一轮 = 两行：user + assistant）
CREATE TABLE IF NOT EXISTS chat_messages (
    id BIGSERIAL PRIMARY KEY,
    session_id BIGINT NOT NULL REFERENCES chat_sessions(id) ON DELETE CASCADE,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role VARCHAR(20) NOT NULL,                -- user / assistant
    content TEXT NOT NULL,
    scene VARCHAR(20),                        -- 该轮判定场景，analytics 用，不参与还原
    rewritten_query TEXT,                     -- 改写后的 query，调试/分析用
    degraded BOOLEAN NOT NULL DEFAULT FALSE,  -- 该轮是否走了 bge 降级通道
    emotion_alert BOOLEAN NOT NULL DEFAULT FALSE,
    token_count INT,                          -- 计费预留；流式结束拿到 usage 后回填 assistant 行
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_chat_messages_session_created ON chat_messages(session_id, created_at);
CREATE INDEX IF NOT EXISTS idx_chat_messages_user_created ON chat_messages(user_id, created_at);

COMMENT ON TABLE chat_messages IS '聊天消息；assistant 行缺失 = 该轮生成失败';
COMMENT ON COLUMN chat_messages.id IS '消息主键';
COMMENT ON COLUMN chat_messages.session_id IS '所属会话，级联删除';
COMMENT ON COLUMN chat_messages.user_id IS '所属用户（冗余，按用户查历史/越权校验用），级联删除';
COMMENT ON COLUMN chat_messages.role IS '消息角色：user / assistant';
COMMENT ON COLUMN chat_messages.content IS '消息正文';
COMMENT ON COLUMN chat_messages.scene IS '该轮判定场景（6 值之一），仅统计/回放用，还原不读';
COMMENT ON COLUMN chat_messages.rewritten_query IS 'LLM 改写后的 query，调试/分析用';
COMMENT ON COLUMN chat_messages.degraded IS '该轮是否走了 bge 本地降级通道（非 LLM 判定）';
COMMENT ON COLUMN chat_messages.emotion_alert IS '该轮是否触发情绪预警（安全树洞）';
COMMENT ON COLUMN chat_messages.token_count IS 'token 用量，计费预留；流式结束拿到 usage 后回填 assistant 行';
COMMENT ON COLUMN chat_messages.created_at IS '落库时间';

-- 10. 会话摘要（一会话一条；增量刷新，向量副本进 chroma chat_summaries）
CREATE TABLE IF NOT EXISTS chat_session_summaries (
    session_id BIGINT PRIMARY KEY REFERENCES chat_sessions(id) ON DELETE CASCADE,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    summary TEXT NOT NULL DEFAULT '',
    message_count INT NOT NULL DEFAULT 0,      -- 摘要已覆盖的消息数（进度标记）
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_chat_session_summaries_user ON chat_session_summaries(user_id);

COMMENT ON TABLE chat_session_summaries IS '会话摘要：每跨 10 条消息异步刷新；embedding 存 chroma collection chat_summaries，库内不存向量（不引 pgvector）';
COMMENT ON COLUMN chat_session_summaries.session_id IS '所属会话，主键兼外键，级联删除';
COMMENT ON COLUMN chat_session_summaries.user_id IS '所属用户（冗余，隔离/删除用），级联删除';
COMMENT ON COLUMN chat_session_summaries.summary IS '摘要正文，≤100 字；空 = 尚未生成';
COMMENT ON COLUMN chat_session_summaries.message_count IS '摘要已覆盖的消息数（进度标记），刷新时更新';
COMMENT ON COLUMN chat_session_summaries.updated_at IS '摘要最近刷新时间';
```

设计要点：

* `scene` 随消息落库仅用于统计/回放，**还原时不读它**（D2）。

* `token_count` 现在只为 10 月账务线预留，一期可空。

* 用户消息与助手消息分两行插入：用户消息在**生成前**落库（流式中途崩了，用户的话也在，还原一致）；助手消息在**流正常结束后**落库。助手行缺失 = 该轮生成失败，前端还原时显示用户气泡即可。

* user\_id 冗余在 messages / summaries 上（按用户隔离、越权校验、删除都靠它，少一次 join）。

* 摘要表只存文本 + 覆盖进度，**向量一律在 chroma**——库内不引 pgvector，compose 不动（与知识库同策略）。

## 4. API 规格（D5，前端与 Cursor 的唯一依据）

全部挂 `/agent/*`（Go 反代 + JWT 自动覆盖）。响应信封沿用 Python 侧现有风格；user\_id 一律取 ContextVar。

| 方法 & 路径                                                 | 请求                                            | 响应                                                                                                | 说明                                               |
| ------------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `POST /agent/chat/stream`                               | `{message: string, session_id: number\|null}` | SSE：首帧 meta 增加 `session_id`（新建会话时返回新 id），随后 `text` 帧、`[DONE]`                                     | session\_id 为空 → 服务端新建会话                         |
| `GET /agent/sessions?page=1&page_size=20`               | —                                             | `{items: [{id, title, summary, message_count, last_message_at}], total}`                          | 按 last\_message\_at 倒序；summary 供列表预览，为空时前端照常回退   |
| `PATCH /agent/sessions/{id}`                            | `{title: string}`                             | `{id, title}`                                                                                     | 改名；校验归属                                          |
| `DELETE /agent/sessions/{id}`                           | —                                             | `{id}`                                                                                            | 物理删除（级联删消息 + 两级向量，见 §7）                          |
| `GET /agent/sessions/{id}/messages?page=1&page_size=30` | —                                             | `{items: [{id, role, content, created_at}], total}`                                               | **倒序分页**（最新一页在前），前端翻历史往上翻                        |
| `POST /agent/sessions/search`                           | `{query: string}`                             | `{items: [{level, session_id, session_title, message_id?, snippet, created_at}], reply?: string}` | 两级语义检索（§7.2）；**items 为空时 reply 为小喜子固定话术**，前端直接展示 |

错误约定：session 不存在或不属于当前用户 → 404（不区分两种，防枚举）；参数错误 → 400。

## 5. L0 加载与一轮对话时序

### 5.1 L0 改造（`llm_task.py`）

* 进程内 `_histories` 字典**退役**，替换为按会话查库：

```
get_history_by_session(session_id: int, turns: int = 5) -> str
    取该会话最近 turns*2 条消息（按 created_at 倒序取、正序拼），
    格式沿用现状："主人: ...\n小喜子: ..."
```

* `_prepare_turn` 改动点：**历史无条件加载**（2026-09-28 修订，线上已踩坑）。原 `need_rewrite` 门控（query < 10 字或命中关键词才带历史）会让指代类追问——"直接告诉我答案""你还记得吗"——拿不到历史，模型只能瞎猜（实测回复"主子，题目没发"）。改为 `user_id` 存在即加载，5 轮上限不变；`need_rewrite` 与 `precheck_words.yaml` 随之退役。代价是每轮多几百 token，收益是指代解析和树洞连续负面检测都变可靠，划算。

* 降级/early 路径照常，`scene` 仍逐条现算。

### 5.2 一轮对话时序

```
前端                 Python Agent                        Postgres / chroma
 │  POST chat/stream {message, session_id?}                │
 │ ─────────────────────►│                                 │
 │                       │ session_id 为空 → INSERT chat_sessions
 │                       │   （title='', user_id=CtxVar）   │
 │                       │ 校验 session 归属（越权→404）     │
 │                       │ user_id 存在 → get_history_by_session（无条件）
 │                       │ _prepare_turn（理解/检索不变）     │
 │  ◄── SSE meta(含 session_id) ──                         │
 │  ◄── SSE text 帧逐段（task_llm_stream）──               │
 │                       │ 生成前：INSERT user 消息行        │
 │                       │ 流结束：INSERT assistant 行       │
 │                       │   UPDATE sessions(count,last_at)  │
 │                       │ 异步①：首条消息→LLM 生成标题（§8）│
 │                       │ 异步②：嵌入两行进 chat_history（§7）│
 │                       │ 异步③：消息数跨 10 → 刷新会话摘要（§7.3）│
 │  ◄── [DONE] ──                                        │
```

三个异步任务都 fire-and-forget，失败只记日志，**绝不阻塞或影响 SSE 主路径**。

## 6. 会话还原语义（D2）

点击列表项 = 纯前端行为 + 一次分页拉取，服务端无"恢复状态"概念：

1. `GET /agent/sessions/{id}/messages` 拉最近一页，渲染消息气泡；
2. 用户继续发话时，`get_history_by_session` 把末尾 5 轮重载进 prompt——**上下文即状态**；
3. 换设备、重启进程、换浏览器，行为一致（这是相对现在进程内字典的本质提升，也是面试演示点）。

刻意不做：会话级场景记忆、进度的"情绪状态机"。它们引入不一致（消息可删可改，派生状态会漂），收益却只是省一次场景判定。

## 7. 跨会话语义检索（D3 / D6 / D7）

### 7.1 存储布局：两个 collection，两个粒度

| collection       | 粒度  | 内容                      | 写入时机    |
| ---------------- | --- | ----------------------- | ------- |
| `chat_history`   | 消息级 | user 行、assistant 行各一条向量 | 消息落库后异步 |
| `chat_summaries` | 会话级 | 会话摘要一条向量（一会话一条）         | 摘要刷新后异步 |

* 与知识库同 persist 目录、**同一个 bge 嵌入模型实例**（`index_store.init_embedding_model()` 复用，不二次加载模型）。

* metadata 均含 `user_id, session_id`（消息级另含 `message_id, role, created_at`）；user\_id 存字符串值，chroma filter 用。

* 两级互补：**摘要级回答"我之前聊过什么"（找到会话），消息级回答"具体是哪句"（定位消息）**。

### 7.2 查询（`POST /agent/sessions/search`）

```
query → bge 嵌入 → 并行查两个 collection（where user_id = ctx_user_id）
      → 各取 top 20 → bge-reranker-base 精排 → 合并去重：
         会话级命中 → {level: "session", session_id, session_title, snippet: summary 截断 80 字}
         消息级命中 → {level: "message", session_id, session_title, message_id, snippet: 消息截断 80 字}
      → 同会话只留最高一条，总计 ≤ 10 条
```

* **必须**用 metadata filter 按 user\_id 隔离：这是向量库最典型的越权事故（默认全文检索会把别人的聊天搜出来），面试会问。

* 两级全部未命中 → 响应 `items: []` + `reply`：小喜子人设话术（如"奴才不记得主子提过这茬，要不再说细点儿？"），前端直接展示，不显示干巴巴的空列表。

* 删除会话时同步删两个 collection 里 `session_id` 对应的向量。

### 7.3 会话摘要的生成与刷新（D6）

* **触发**：助手消息落库后，`sessions.message_count` 每跨 10 的倍数（10/20/30…，≈每 5 轮）且该轮非降级，异步触发。

* **输入**：该会话全部消息（一期 demo 规模小，全量重摘即可；`summaries.message_count` 只作进度标记，不必做增量拼接）。

* **并发护栏**：进程内 per-session `asyncio.Lock`，进入后先检查 `message_count` 是否已被更新过的摘要覆盖，覆盖则跳过。

* 生成失败只记日志，旧摘要保留；摘要本身用一次非流式 LLM 调用（temperature=0.3，固定 system prompt：总结主人和小喜子聊了什么，≤100 字）。

* 摘要的消费场景：① 会话列表的第二条预览；② 嵌入后做会话级召回（§7.1）。

### 7.4 明确不进一期（面试"规划中"素材）

| 参考设计中的表                             | 我们的处置         | 什么时候加                                               |
| ----------------------------------- | ------------- | --------------------------------------------------- |
| `conversation_chunk_summaries` 分段摘要 | 不进一期          | 会话长到全量重摘超 token / 延迟明显时，换成滚动分段摘要                    |
| `memory_facts` 记忆事实抽取               | 不进一期（二期故事）    | 真要做"记住主子偏好"时，从消息异步抽取 preference / entity / event 事实 |
| pgvector / HNSW                     | 不引，向量在 chroma | 向量规模到十万级、chroma 成为瓶颈时再评估                            |
| Postgres 全文检索                       | 不做（D7）        | 中文分词扩展成熟且确有需求时再评估                                   |

## 8. 自动标题（D4）

* 触发点：会话首条 user 消息落库后，若 `title == ''`，异步发起一次非流式 LLM 调用：
  输入 = 首条用户消息，要求输出 ≤12 字标题（可用固定 system prompt，temperature=0.3）。

* 并发护栏：`UPDATE chat_sessions SET title=? WHERE id=? AND title=''`，受影响行数为 0 则说明别的请求已生成，放弃。

* 降级通道（`degraded=True`）或 LLM 失败时不生成，标题留空——功能无损。

* 成本：每会话一次调用，可忽略。

## 9. 边界与安全

* **鉴权分层**（与 2026-09-28 讨论一致）：token 失效 → Go JWT 中间件 401（前端跳登录）；网关内取不到 user\_id → Go fail-fast 500（Cursor 已加）；Python 收到空头 → 存 None 降级 + WARN，不拒请求（保 CLI/调试路径），生产靠网络隔离 8000 端口。

* **越权校验**：所有 `{id}` 路径先查归属，`sessions.user_id != ContextVar user_id` → 404。

* **向量隔离**：见 §7.2，metadata filter 是硬要求，不是优化。

* CLI 直连路径（无 user\_id）：聊天照常，但不建会话、不落库（无归属可挂）——与现状一致。

## 10. 面试口径

1. **"历史怎么存的？"**——消息和会话摘要落 Postgres，向量副本进 chroma；Agent 域数据归 Python 服务，网关只做鉴权和透传，职责边界清楚。
2. **"为什么不用关键词/全文检索找历史？"**——汉语同词多语境，LIKE 丢语义；Postgres 自带 FTS 对中文没有分词（`to_tsvector('simple')` 把整句变成一个 token），要 pg\_jieba 这类扩展才可用，为一个小功能动 compose 不值。所以做两级语义检索：会话摘要级找"聊过什么"，消息级找"具体哪句"，一套 bge 模型三个用途（场景匹配、知识库、历史检索）。
3. **"摘要怎么生成的？"**——每跨 10 条消息异步全量重摘，一次 LLM 调用；摘要一份两用：列表预览 + 嵌入做会话级召回；规模大了再换滚动分段摘要（参考设计的 chunk 方案，规划中）。
4. **"多轮上下文怎么恢复？"**——服务端无会话状态，状态=消息本身；还原 = 分页拉消息渲染，续聊 = 末尾 5 轮重载进 prompt，换设备行为一致。
5. **"向量库怎么防越权？"**——查询强制 metadata filter user\_id；这是向量库最常见事故点，我在设计里把它定为硬约束。

## 11. 实施顺序

1. `.env` 加载修复 + Python 连 Postgres（前置）。
2. 迁移 SQL（migrate\_0003 + init.sql 同步改注释）。
3. 消息落库：`_prepare_turn`/`task_stream` 接 session\_id，生成前存 user 行、流后存 assistant 行；`_histories` 退役。
4. L0：`get_history_by_session` 替换 `get_history_by_user_id`。
5. 会话 API：列表 / 改名 / 删除 / 消息分页。
6. 语义检索：`chat_history` + `chat_summaries` 两个 collection + search API（两级召回）。
7. 会话摘要异步刷新（D6）。
8. 自动标题。
9. 前端（Cursor，按 §4 规格）。
