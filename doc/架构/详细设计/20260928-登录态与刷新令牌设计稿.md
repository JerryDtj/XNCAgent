# 20260928-登录态与刷新令牌设计稿（cookie 方案）

> 状态：待邓天骄定稿
> 现状（Go 仓已确认）：access 2h + refresh 7d，登录接口把双 token 返回 JSON；**无 /refresh 端点、无 cookie 写入**；`refresh_tokens` 表支持删行吊销
> 目标：登录后一周内免重新发验证码；不放大 access token 的失窃窗口

## 1. 决议

| 凭证 | 存放 | 寿命 | 轮换 |
|------|------|------|------|
| refresh token | **httpOnly cookie**（JS 不可读） | 7 天（与 DB `expires_at` 一致，绝对过期） | 每次 /refresh **旋转**：旧 token 立即作废，发新并同步写 cookie |
| access token | 前端**内存**（JS 变量，不落任何存储） | 2 小时不变 | 过期靠 /refresh 重新拿 |

配套新端点 `POST /api/v1/users/refresh`（Go 侧，auth 核心，**自己写**）：

- 请求：仅携带 cookie，无 body。
- 成功 200：`{code, message, data: {access_token, expires_in}}`，同时 `Set-Cookie` 下发新 refresh token。
- 失败 401：cookie 缺失 / token 不存在 / 已过期 / 已被旋转作废 → 前端跳登录页。
- 校验：cookie 值对照 `refresh_tokens` 表；通过后**先删旧行、插新行**（旋转），并发两个 /refresh 只有一个赢（后者校验时旧行已不存在 → 401，用户重新登录，可接受）。

连带改动三处：

1. **JWT 中间件白名单**加 `/api/v1/users/refresh`（现有白名单：/health、register、login）。
2. **登录响应 body 不再返回 `refresh_token`**——refresh 只存在于 cookie，避免两份副本不一致；body 只留 `access_token` + `expires_in`。
3. **新增 `POST /api/v1/users/logout`**（一期建议做，体量极小）：删 `refresh_tokens` 行（吊销）+ 清 cookie + 返回 200。登出后可吊销是面试卖点，不做就只能等 7 天自然过期。

## 2. cookie 属性

| 属性 | 值 | 理由 |
|------|----|----|
| Name | `refresh_token` | — |
| HttpOnly | true | JS 读不到，防 XSS 偷令牌（cookie 派的核心收益） |
| SameSite | Lax | 防 CSRF 主力：现代浏览器拦跨站 POST 携带 |
| Secure | 生产 HTTPS 时开启 | 防链路窃听；本地 http 开发期可关 |
| Path | `/api/v1/users` | 收窄到用户域：refresh 与 logout 都要读这个 cookie（2026-09-30 修正：原设计写成 `/api/v1/users/refresh`，Path 不覆盖 logout 会导致登出时浏览器不带 cookie、库内吊销落空）。同域下 `/me` 等请求也会携带，但这些接口认 Bearer 头，多带无害 |
| Max-Age | 7 天（604800s） | 与 DB `expires_at` 对齐 |

## 3. 安全口径（面试问答）

1. **"为什么 refresh 放 cookie、access 放内存？"**——cookie 的 HttpOnly 对 XSS 免疫但会随请求自动携带（CSRF 面），localStorage 反之；所以长寿命凭证放 httpOnly cookie + SameSite + Path 收窄，短寿命凭证放内存。两头各取所长。
2. **"refresh 为什么要旋转？"**——一次一密：cookie 被窃取后攻击者先用掉，合法用户再用旧 token 就会 401——旧 token 重放本身可作为被盗信号（收到"已旋转"的 401 可记 WARN）。
3. **"怎么吊销？"**——refresh token 落库，登出即删行；access token 2 小时自过期，吊销窗口有界。
4. **"CSRF 怎么防？"**——SameSite=Lax 挡跨站携带为主，Path 收窄减少攻击面；如需更严可加 Origin 校验。一期不加 CSRF token。

## 4. 前端流程规格（Cursor 实现依据）

技术栈以 XNCAgent-frontend 现状为准，不指定框架：

1. **app 启动**：先 `POST /api/v1/users/refresh`（`withCredentials: true`）→ 200 拿 `access_token` 存**内存变量**，进入应用；401 → 跳登录页。
2. **每次 API 请求**：拦截器自动加 `Authorization: Bearer <access_token>`（主 API 走 Bearer，不依赖 cookie）。
3. **任意请求收到 401**：自动调一次 /refresh，成功则**重放原请求**；再 401 → 清空内存 token，跳登录页。
4. **登录成功**：body 取 `access_token` 存内存；refresh 在 httpOnly cookie 里，前端**不读、不写、不存**。
5. **登出**：`POST /api/v1/users/logout`（withCredentials）→ 清空内存 token → 跳登录页。
6. **API_BASE** 从环境变量读（Vite 用 `VITE_API_BASE`），不硬编码。
7. 若现有登录代码把 token 存了 localStorage/sessionStorage，一律改成内存存储。

## 5. 明确不做（一期）

- 滑动过期（每次刷新顺延 7 天）：绝对过期够用，二期再说。
- CSRF token / 双提交校验：SameSite=Lax + Path 收窄够一期。
- access token 黑名单：2h 短寿命自过期，无需吊销列表。
